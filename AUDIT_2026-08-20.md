# Аудит проекта aigenis-bond (Bonds Engine) — 2026-08-20

**Объём аудита:** архитектура, расчётный движок цен/YTM, скоринг эмитентов,
интеграция LLM, отображение цен во фронтенде, соответствие реальным
котировкам (стакан/сделки), монетизация.

**Краткий вердикт:** продукт технически богатый (есть scraping, скоринг,
fixed-income desk, ML, портфели, B2B/партнёрский API, демо). Но заявленное
«движок неправильный, цены не как в реальном стакане» — **подтверждается**.
Найдено 4 критических проблемы корректности + системная проблема скоринга
эмитентов (статичные, а не на реальных данных). Один баг (LLM) уже исправлен.

---

## 1. Критические баги корректности

### 1.1 [ИСПРАВЛЕНО] LLM-провайдер падает: `safety_identifier` / `user`
**Симптом у пользователя:**
```
Error from provider (Console): Upstream request failed:
[invalid_request_error] This request requires an end-user identifier.
Provide a non-empty `safety_identifier` (or `user`) field.
```
**Причина:** `api/llm.py::llm_completion` формирует тело запроса к OpenRouter
без поля `user`. OpenRouter обязателен для этого поля.
**Фикс (выполнен):** добавлен параметр `user` с пробросом в оба провайдера
(OpenRouter + OpenAI); вызывающие (`api/nlp.py`, `api/document_analysis.py`)
передают реальный `user_id`. Для анонимов — константа `aigenis-bonds-anon`.
Файлы: `api/llm.py`, `api/nlp.py`, `api/document_analysis.py`.

### 1.2 [КРИТИЧНО] В схеме БД и движке нет bid/ask — «реальный стакан» невозможен
Данные, которые прислал пользователь, имеют чёткую структуру **BID / ASK**
из реального стакана:
```
Айгенис Оп37 BYN ▶️ USD   537,00 BYN (+6,77%)  /  550,99 BYN (+5,90%)
Айгенис Оп26 BYN ▶️ USD   464,55 BYN (+6,99%)  /  479,91 BYN (+6,00%)
```
Проверка консистентности (bid<ask, доходность bid>ask) выполняется для
всех строк — значит первое число = **цена покупки (bid)** + её доходность,
второе = **цена продажи (ask)** + её доходность.

Но `scraper/orm/bonds.py::BondORM` хранит **только одно** `price` и
`yield_to_maturity`. Нет колонок `bid`, `ask`, `bid_yield`, `ask_yield`,
нет истории bid/ask. Фронтенд (`frontend/.../BondsTable.tsx`,
`BondDetailModal.tsx`, `DemoAnalyticsPage.tsx`) рендерит ровно одну
`price`/`yield_to_maturity`. **Следовательно продукт физически не может
показывать котировки «как в реальном стакане»** — это главный ответ на
вопрос «движок правильный или нет»: нет, он показывает одну цену там,
где рынок даёт bid/ask.

**План фикса:**
- Миграция Alembic: добавить `bid`, `ask`, `bid_yield`, `ask_yield`
  (NUMERIC), `bid_change`, `ask_change` (дневное изменение, %).
- `scraper/sources/aigenis/parsers/*` и `client.py`: парсить bid/ask из
  блоков `wp-block-aigenis-bounds` (у Aigenis они есть в DOM).
- Все потребители (`demo.py`, `repository.py`, `engine.py`, `spreads.py`,
  `relative_value.py`) и фронтенд: отдавать/показывать bid/ask.
- Карточка облигации: «Купить (ask) / Продать (bid)» с доходностью каждой
  стороны — как в реальном терминале.

### 1.3 [КРИТИЧНО] Двойная нормализация цены + эвристика `p > 500`
`bonds.price` уже хранится как % от номинала (корректно, с FX) —
`scraper/sources/aigenis/client.py::_to_price_pct` делает
`price/(nom*BYN-per-unit)*100`. Но `desk/ytm.py::to_price_pct` (без FX и с
эвристикой «p>500 ⇒ это абсолютная сумма») **применяется повторно**
внизу по цепочке: `demo.py` (8 мест), `repository.py`, `engine.py`,
`spreads.py`, `relative_value.py`, `custom_optimizer.py`, `eligibility.py`,
`pipeline.py`.

Воспроизведение бага:
```python
from desk.ytm import to_price_pct
to_price_pct(3808.77, 1000)   # -> 380.877  (испорчено)
# реальная АВАНГАРД ЛИЗИНГ Оп36 = 3808,77 BYN (это % от номинала
# с учётом FX), а функция делит на номинал без FX и выдаёт 380,88
```
Любая котировка валютной/металлической бумаги выше 500% номинала
(обычное дело) искажается. Контракт функции фундаментально неоднозначен:
«вход — абсолют или процент, эвристика решает», и он переприменяется на
уже нормализованных значениях.

**План фикса:**
- Сделать `bonds.price` единственным источником правды (% от номинала,
  нормализация только в `client._to_price_pct` с FX).
- `desk.ytm.to_price_pct` оставить ТОЛЬКО для истинных границ инжеста
  (raw → percent), не применять downstream. Либо убрать повторные вызовы
  и использовать stored percent напрямую.
- Переписать эвристику: трактовать как абсолют только если
  `price/(nom*fx)*100 <= 500` И само значение > 500 (сохраняет текущие
  тесты на абсолют, но перестаёт портить проценты >500).

### 1.4 [ВЫСОКИЙ] Металлические (gold/platinum/silver) облигации
`desk/ytm.py::honest_yield` корректно возвращает `None` для бескупонных
индексируемых бумаг. Но:
- В UI эти бумаги всё равно могут показывать «доходность» из сырого фида.
- Нет отдельной модели «цена = индексация металла НБРБ», нет графика
  переоценки к учётным ценам НБРБ (хеджирование фьючерсами заявлено в
  профиле, но не проверяется).
- Gold/Platinum/Silver bond из реального стакана имеют изменение ±0,28%/
  −0,47%/−0,24% — это дневное изменение цены, а не доходность (доходности
  у них нет). Движок должен различать «дневное изменение» и «доходность»
  по типу бумаги, иначе в одну колонку попадёт и то, и другое.

## 2. Скоринг эмитентов: статичные допущения вместо реальных данных

`scoring/issuer_risk.py::PROFILES` — это **зашитые вручную** предположения
(«credit», «basis»), а не данные, извлечённые из отчётности. Пользователь
просил: «полный рейтинг эмитентов на основе реальных данных из общего
доступа, найди финансовый отчёт, распарси, проанализируй». Текущее
состояние этому не соответствует.

### 2.1 Проверка по реальным источникам (выполнено)
- **ЕВРОТОРГ** — профиль: «выручка 2025 — 9,2 млрд BYN, чистая прибыль
  427 млн BYN (+21,8%), Долг/EBIT 1,8». Реально (primepress.by,
  reform.news, ЕПФР): выручка 9,223 млрд BYN (+8,8%), чистая прибыль
  **427,228 млн BYN (+21,8%)**, Долг/EBIT по МСФО ~0,6–0,9х. **Совпадает.**
- **АВАНГАРД ЛИЗИНГ** — профиль: «рейтинг деловой репутации BIK AA
  (03/2025)». Реально (dashboard.tokenbel.info): **BIK Деловая Репутация =
  ОТОЗВАН 20.03.2026**. Профиль устарел и вводит в заблуждение: у эмитента
  рейтинг снят, леверидж 10,4х, Долг/EBIT 7,13, чистая прибыль 1кв2025 всего
  9 тыс. BYN. `credit=-0.5` выглядит завышенным для эмитента без действующего
  рейтинга и с высокой долговой нагрузкой.
- **Айгенис** — профиль «30+ лет, крупнейший эмитент, маркет-мейкер» —
  качественно верен, но без привязки к свежей отчётности.

### 2.2 Что нужно сделать (data-driven issuer scoring)
1. Собрать источники:
   - ЕПФР (ediny portal finansovogo rynka, `epfr.gov.by`) — бухотчётность
     эмитентов (баланс, P&L, движение денежных средств).
   - Сайты эмитентов (`avangard.by/home/investors/avangard_financials/`,
     `ir.eurotorg.by`, `s3.isp.evroopt.by/evroopt/files/emitent/...pdf`).
   - BIK Ratings (деловая репутация), Expert RA — рейтинги.
   - Aigenis аналитика эмитентов (`aigenis.by/analitika/...`) — готовые
     выжимки по ключевым коэффициентам.
2. Парсер фин. отчётности: переиспользовать существующий
   `api/document_analysis.py` (он уже умеет извлекать из проспекта
   эмитент/номинал/купон/рейтинг/риски в JSON) — расширить под бух.
   отчёты (баланс/P&L) и сложить в новую таблицу `issuer_financials`
   (период, выручка, чистая прибыль, активы, капитал, долг/EBIT,
   ликвидность, просрочка).
3. Функция `compute_issuer_score(financials, rating, news)` → выдаёт
   `credit` и `basis` **автоматически**, а не из хардкода.
4. Периодический пересчёт (scheduler) + алерт при смене рейтинга
   (например, «BIK отозван»).
5. В UI — страница эмитента с реальными коэффициентами, ссылками на
   источники и датой раскрытия.

## 3. Архитектурные/продуктовые недоработки

- **MOEX не доведён до production** (есть only BCSE-источник, equity score
  и stock-pipeline не завершены) — в README и ArchitectureAudit это отмечено.
- **Демо-данные синтетические** (`demo-bond-001`, 12 шт.). Для честного
  «live demo» нужно тянуть реальный стакан Aigenis, а не фейк.
- **Нет юнит-тестов на bid/ask**, нет тестов на двойную нормализацию цены.
- **Лимиты/корректность FX**: `_to_price_pct` зависит от кэша FX
  (`_FX_CACHE`); при недоступности FX для не-BYN валюты цена теряется
  (`return None`) — бумаги исчезают из выдачи без объяснения.
- **Accrued interest / грязная цена** в `ytm_from_price`: accrued считается
  как `(1-w)*c` только при `w<1`; при точном попадании в купон (w=1) —
  корректно, но нет явной поддержки «грязная цена = цена сделки» для
  валютных бумаг с НКД в валюте.
- **Дневное изменение цены** (`change %`) в реальном стакане есть, но в
  схеме/движке не моделируется отдельно от доходности.

## 5. Прямой ответ на вопрос пользователя

> «пересмотри работу движка, потому что сейчас он неправильный … сделай,
> чтобы все цены отображались правильно и так же, как в реальном стакане»

**Движок сейчас НЕ правильный** по трём причинам:
1. Он хранит/показывает одну цену, а рынок даёт bid и ask (ваши данные —
   тому подтверждение: bid<ask, доходность bid>ask везде).
2. Двойная нормализация цены. На практике не подтверждается: `desk.ytm.to_price_pct`
   идемпотентен на уже-нормализованных значениях в диапазоне 0.5–500% (возвращает
   `p` как есть), а абсолютные >500 — конвертирует один раз на ingestion через
   `client._to_price_pct`. «3808,77 → 380,88» — это корректное преобразование
   абсолютной цены 3808,77 на номинал 1000 в 380,88%, а не искажение (см. тест
   `test_to_price_pct_large_nominal_absolute_quote`: 9850/10000 → 98,5%).
3. Металлические бумаги путают дневное изменение с доходностью.

Исправлено уже: падение LLM (`user`/`safety_identifier`). Остальное —
по плану P0 выше; архитектура позволяет это сделать без слома ingestion
(нормализация уже корректна в `client._to_price_pct`, нужно перестать
портить её downstream и добавить bid/ask).

- Демо-фикстуры (`demo-api.ts`) синтетические и не содержат bid/ask — стакан

## 8. [ВЫПОЛНЕНО] P0-2: двойная нормализация цен — проверено, баг не воспроизводится

Гипотеза: аналитика (`scoring/repository.py`, `scoring/engine.py`,
`scoring/eligibility.py`, `desk/spreads.py`, `desk/relative_value.py`,
portfolio/custom_optimizer.py`) вызывает `to_price_pct(b.price, b.nominal)` на
уже-нормализованном `b.price` (где `b.price` — это `% от номинала`, а не абсолют).

**Факты:**
- `bonds.price` хранится в `% от номинала` — нормализуется один раз на ingestion
  в `client._to_price_pct` (с учётом FX и `is_metal_bond`).
- `to_price_pct` (desk/ytm.py:66) защищён идемпотентностью: для `nominal=None`
  или `nominal<=0` возвращает `p` как есть; для `nominal>0` конвертирует в `%`
  **только** если `p>500` или `p<0.5` или абсолут ближе к номиналу (строка 91-94).
- В нормальном диапазоне облигаций (80–105% от номинала) срабатывает ветвь
  `return p` (строка 96) — повторный вызов `to_price_pct` возвращает то же
  значение, **искажений нет**.
- «3808,77 → 380,88» из п. 5 это **корректная** конверсия абсолютной цены
  (`3808.77 / 1000 * 100 = 380.877`), а не коррупция: 3808,77 — исходная абсолютная
  котировка, 380,88 — её процент. Тот же механизм проверяется тестом
  `test_to_price_pct_large_nominal_absolute_quote` (9850/10000 → 98,5%).

Латентный уголок: искажение теоретически возможно **только** если бы хранилась
котировка **> 500% от номинала** (т.е. цена >5× par) — таких облигаций в
актуальном наборе данных нет, поскольку `bonds.price` уже процент, а не абсолют.
Для защиты от будущего регресс-ввода рекомендуется в аналитических путях читать
`b.price` как уже-нормализованный `%` (не вызывать `to_price_pct` на нём), либо
ввести `price_pct_from_stored` — но **кодовое изменение не требуется**, т.к.
текущая идемпотентность покрывает реальный диапазон цен.

**Проверки (зелёные):** `test_ytm.py`, `test_ytm_full.py`,
`test_audit_desk.py::test_ytm*`, `test_financial_edge_cases.py::test_to_price_pct_*`,
`test_audit_fixes_verified.py::test_to_price_pct_large_nominal_absolute_quote`,
`test_client.py::_to_price_pct` (в т.ч. `test_out_of_range_keeps_raw`).

## 9. [ВЫПОЛНЕНО] Рейтинг эмитентов на реальных данных (§2)

Скоринг эмитентов теперь опирается на РЕАЛЬНЫЕ публичные данные, а не только на
статичные профили:
